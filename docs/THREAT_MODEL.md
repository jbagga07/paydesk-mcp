# PayDesk MCP - Threat Model Document

This document outlines the security threats identified for the PayDesk MCP system, evaluating their impact and likelihood, and demonstrating the architectural mitigations implemented.

---

| ID | Threat Category | Threat Description | Impact | Likelihood | System Mitigation / Defense |
|:---|:---|:---|:---|:---|:---|
| **1** | **Prompt Injection** | A user injects malicious system instructions into ticket titles or descriptions, attempting to override the LLM's behavioral rules. | Medium | High | **Strict Text Isolation**: Data retrieved from MongoDB or Postgres is formatted strictly as JSON/plain text payloads. The server does not execute text contents as code. |
| **2** | **Indirect Prompt Injection** | An LLM reads a support ticket that was created by a third party, containing instructions to leak other records or trigger a payout. | High | Medium | **API Scoping and Approval Gates**: The LLM cannot perform any state-changing action without passing `approved=True`. The approval status is always visible, and critical commands require explicit confirmation. |
| **3** | **Cross-Merchant Data Leakage** | A merchant caller queries the transaction details, balance, or API keys belonging to another merchant. | Critical | High | **Boundary Scoping Layer**: The security scope layer overrides caller inputs. If a merchant caller passes `merchant_id="MER-1001"` but is logged in as `MER-1005`, the system overrides the parameter to `MER-1005`. |
| **4** | **Unauthorized Tool Execution** | A caller attempts to execute admin-only operations (e.g. balance adjustment or updating fee schedules). | Critical | Low | **Scope validation**: The `is_authorized` helper validates scopes (`ledger:write`) and roles (`role == 'ADMIN'`) before calling database handlers. |
| **5** | **Broken Authentication** | A caller accesses resources without passing a valid security context. | Critical | Medium | **BearerAuthMiddleware**: Registered in Starlette, the middleware intercepts every request to `/mcp`, decodes the JWT, and fails with a `401 Unauthorized` if invalid. |
| **6** | **Broken Authorization** | A caller has a valid token but lacks the specific scope required for the requested tool (e.g., support agent reading balance). | High | Medium | **Granular Scopes**: Scopes are checked per-tool using `@mcp.tool` and `@audit_logged` wrappers. `ledger:read` is verified for financial actions, separating it from `txn:read`. |
| **7** | **Privilege Escalation** | A merchant caller modifies their context or injects claims to escalate roles to ADMIN. | Critical | Low | **Cryptographically Signed JWTs**: The JWT is signed with `JWT_SECRET` (loaded securely from `.env`). Callers cannot forge token payloads or roles. |
| **8** | **Leaked API Tokens** | A developer's API key is exposed, allowing attackers to access the merchant account. | Critical | Medium | **One-time Secret display & Hashing**: When created via `create_api_key`, the clear-text token is displayed only once. Its hash is stored in Redis, and metadata can be revoked instantly via `revoke_api_key`. |
| **9** | **Leaked Database Credentials** | Database passwords, host ports, or API secrets are committed to git repositories. | Critical | High | **Dotenv & Gitignore**: Secrets are removed from codebase files and loaded via `.env`. A `.gitignore` prevents local env files from being committed, leaving only `.env.example` in repo. |
| **10** | **Audit Log Tampering** | An attacker deletes or modifies audit logs to hide unauthorized transactions. | High | Low | **Read-only audit tools**: Audit logs are stored in a dedicated MongoDB collection (`audit_logs`). Only users with the role `ADMIN` can retrieve logs; there are no write/update tools exposed for logs. |
| **11** | **Replay Attacks** | An attacker intercepts a valid JSON-RPC request and re-sends it to execute duplicate payouts. | High | Low | **TLS Encryption & Token Expiry**: Self-signed SSL certificates secure the HTTP transport. JWT tokens have an expiry configuration (`exp` claim) to invalidate old sessions. |
| **12** | **Malicious MCP Clients** | A client connects and tries to execute tools without establishing a valid session. | High | Medium | **Session binding**: The HTTP transport requires an `mcp-session-id` header alongside the Authorization Bearer token to route JSON-RPC requests, preventing stateless sweeps. |
| **13** | **Denial of Service (DoS)** | A merchant floods the MCP server with high-frequency tool calls, exhausting database connection pools. | Medium | Medium | **Redis Rate Limiting**: The `get_rate_limit_status` tool queries Redis counter buckets to track and enforce request quotas per merchant. |
| **14** | **Data Exfiltration** | An attacker calls list endpoints with huge limits to extract complete merchant databases. | High | Medium | **Query Pagination & Limits**: All listing tools (disputes, transactions, payouts) enforce maximum query limits (default 10, capped at 100) at the application layer. |
| **15** | **Sensitive Logging** | The audit logger writes clear-text API keys or client passwords into database logs. | High | Low | **Key Prefixes & Sanitization**: The `create_api_key` tool writes only the key prefix (`pk_live_abcd...`) and metadata to logs and Redis hashes; secret tokens are never written to audit trails. |
